# WSS relay for Telegram Desktop MTProto mux tunnel

## Deploy checklist

1. DNS A/AAAA for your domain.
2. Install server prerequisites (Go 1.22+, systemd, curl, OpenSSH).
3. Deploy relay: `./deploy.sh root@HOST` (builds on the server into `/opt/wss-relay`).
4. Configure edge proxy (Caddy/nginx) — see `Caddyfile.example` / `nginx.conf.example`.
5. Add token hashes to `/opt/wss-relay/config/tokens`, redeploy or restart service.
6. Open firewall for the TLS port (443 or custom, e.g. 3443).
7. In tdesktop: `tg://wss?server=HOST&port=443&tunnels=6`.

## Server layout

```text
/opt/wss-relay/
  bin/wss-relay          # built binary
  src/                   # synced sources (remote build)
  config/tokens          # SHA-256 token hashes (optional auth)
```

Systemd unit: `/etc/systemd/system/wss-relay.service` (generated by deploy).

## Prerequisites (remote server)

| Component | Purpose |
|---|---|
| Go 1.22+ | build relay on server |
| systemd | service management |
| curl | post-deploy health check |
| user `nobody` | service runtime user |
| OpenSSH | deploy over SSH |

Install Go 1.22+ if the distro package is too old: https://go.dev/dl/

Edge proxy (Caddy or nginx) is configured separately — not required for relay itself.

## Deploy script

From `tools/wss-relay/` on your workstation:

**Linux / macOS / WSL / Git Bash:**

```bash
chmod +x deploy.sh remote-build.sh
./deploy.sh root@31.76.21.175
```

**Windows (PowerShell or cmd):**

```powershell
cd tools\wss-relay
.\deploy.ps1 root@31.76.21.175
```

```cmd
deploy.cmd root@31.76.21.175
```

Requires OpenSSH Client (`ssh`, `scp`) and `tar` (built into Windows 10+). Optional: `rsync` (e.g. from Git for Windows) for faster sync.

What it does:

1. Checks local `ssh` (+ `rsync` or `tar`+`scp`).
2. Syncs sources to `/opt/wss-relay/src/`.
3. On the server: checks Go/systemd/curl, builds `bin/wss-relay`, installs systemd unit, restarts service, verifies `/stats/json`.

Options (same for `deploy.sh`, `deploy.ps1`, `deploy.cmd`):

```bash
./deploy.sh --check-only root@HOST    # prerequisites + sync, no restart
./deploy.sh --listen 127.0.0.1:8283 root@HOST
```

```powershell
.\deploy.ps1 --check-only root@HOST
.\deploy.ps1 --listen 127.0.0.1:8283 root@HOST
$env:INSTALL_DIR = '/opt/wss-relay'; .\deploy.ps1 root@HOST
```

Manual remote steps (without deploy script):

```bash
rsync -az --delete -e ssh ./ root@HOST:/opt/wss-relay/src/
ssh root@HOST 'INSTALL_DIR=/opt/wss-relay bash /opt/wss-relay/src/remote-build.sh deploy'
```

## Manual install (first time)

```bash
mkdir -p /opt/wss-relay/{bin,config,src}
# copy sources into /opt/wss-relay/src/, then:
cd /opt/wss-relay/src
go build -ldflags='-s -w' -o /opt/wss-relay/bin/wss-relay .
cp auth.tokens.example /opt/wss-relay/config/tokens
chmod 640 /opt/wss-relay/config/tokens
chown root:nobody /opt/wss-relay/config/tokens
# install wss-relay.service.example → /etc/systemd/system/wss-relay.service
systemctl daemon-reload && systemctl enable --now wss-relay
```

Prefer `./deploy.sh` — it runs the same steps with checks.

## Client link format

```
tg://wss?server=HOST&port=443&tunnels=6&token=TOKEN
```

Path is always `/ws/mux` on the client. `tunnels` is the number of parallel mux WebSocket connections (1–9, default 6). `token` is optional unless relay auth is enabled.

## Authentication

Relay accepts (when `-auth-file` or `-auth-token` is set):

- `Authorization: Bearer <token>`

Token file (`/opt/wss-relay/config/tokens`, see `auth.tokens.example`): one **SHA-256 hex hash** per line. Generate:

```bash
printf 'my-secret-token' | sha256sum | awk '{print $1}'
```

Deploy creates `config/tokens` from the example on first run if missing. Edit hashes on the server, then `systemctl restart wss-relay`.

Flags:

- `-auth-file` — path to hash list (recommended)
- `-auth-token` — single plaintext token (dev/single-user only)

Without either flag, mux accepts anonymous connections (backward compatible).

## Limits

Relay flags (defaults in `wss-relay.service.example` / deploy output):

- `-max-tunnels-per-ip` — max concurrent mux WebSocket tunnels (`/ws/mux`) per client IP. Default `12` (about `tunnels × 2` for reconnect overlap). `0` disables the limit.
- `-max-streams` — max MTProto streams inside one mux tunnel. Default `64`.
- `-stream-idle-timeout` — close mux streams with no traffic for this long. Default `10m`. `0` disables.
- `-ws-ping-interval` — WebSocket ping interval per tunnel. Default `30s`. `0` disables.
- `-ws-read-timeout` — WebSocket read deadline, extended on traffic or pong. Default `90s`. `0` disables.
- `-telegram-only` — allow upstream TCP only to Telegram DC subnets from [cidr.txt](https://core.telegram.org/resources/cidr.txt). Default `true`. Set `false` only for local testing.

On the edge proxy, keep `read_timeout` / `write_timeout` near `2m` (see `Caddyfile.example`) so dead client connections do not keep relay tunnels open for hours.

Upstream targets are checked before dial (including DNS for hostnames) and again on the connected peer address.

Client IP is taken from `X-Real-IP`, then the first hop in `X-Forwarded-For`, then `RemoteAddr`. Set those headers only from a trusted reverse proxy.

Optional nginx edge guard: `limit_conn` on `/ws/mux` (see `nginx.conf.example`).

## Monitoring

Live dashboard on the relay listen address (`127.0.0.1:8283`):

- UI: `/stats` (auto-refresh every 2s)
- JSON: `/stats/json`
- Prometheus: `/stats/metrics`

Disable with `-stats-path=""`. On the server, open via SSH tunnel:

```bash
ssh -L 8283:127.0.0.1:8283 root@HOST
```

Then browse `http://127.0.0.1:8283/stats`. The dashboard has a **Restart relay** button (requires the same Bearer token as mux when auth is enabled).

Service unit uses `Restart=always` so the relay can restart itself via `POST /stats/restart` without sudo.

```
tdesktop --TLS+WS+mux--> edge:443 --WS--> wss-relay:8283 --TCP--> Telegram DC
```
